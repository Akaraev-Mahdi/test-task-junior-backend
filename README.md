## Обзор реализации

В рамках тестового задания была реализована фича настройки периодичности задач. Система позволяет врачам создавать шаблоны, на основе которых автоматически генерируются рабочие задачи на конкретные дни.

## Принятые архитектурные решения

1. **Разделение на Шаблон и Экземпляр (IsTemplate)**
Для решения проблемы «замусоривания» базы и бесконечного дублирования введена концепция `is_template.`
    - Задачи, созданные через API, помечаются как **шаблоны** `(is_template: true).`
    - Задачи, созданные воркером, являются **экземплярами** `(is_template: false).`
    - Это позволяет хранить настройки периодичности только в одном месте и четко разделять «правило» создания от самой «работы».

1. **Хранение настроек в JSONB**
Настройки периодичности `(recurrence)` хранятся в базе данных Postgres в формате `JSONB.` Это обеспечивает максимальную гибкость. Если в будущем клиенту потребуется новый тип периодичности (например, «каждый второй четверг месяца»), нам не придется менять схему БД — достаточно будет обновить логику в коде Go.

3. **Фоновый процесс (Background Worker)**
Генерация задач происходит в отдельной горутине, которая «просыпается» по таймеру (в продакшене — раз в сутки).
Это гарантирует высокую производительность API. Пользователь не ждет, пока система вычислит все задачи на год вперед; система делает это постепенно в фоновом режиме.

4. **Защита от дублирования (Idempotency)**
Реализована проверка через поле parent_id. Перед созданием задачи воркер проверяет, не создавался ли уже экземпляр от этого шаблона на текущие сутки. Предотвращает создание лишних копий при перезапуске сервера или сбоях таймера.

5. **Улучшение UX (Ясность для врача)**
В заголовки автоматически генерируемых задач добавляется дата в формате `[ДД.ММ].` Помогает персоналу мгновенно ориентироваться в списке однотипных ежедневных задач.

## Примеры запросов (для тестирования)
Эти JSON-объекты можно использовать в Postman для проверки всех сценариев из ТЗ.

**1. Ежедневная задача (каждый 2-й день)**
```json
{
  "title": "Обход палат",
  "description": "Проверить состояние пациентов в реанимации",
  "recurrence": {
    "type": "daily",
    "interval": 2
  }
}
```
**2. Ежемесячная задача (15-го числа)**
```json
{
  "title": "Инвентаризация склада",
  "description": "Сверка остатков медикаментов",
  "recurrence": {
    "type": "monthly",
    "day_of_month": 15
  }
}
```
**3. Четные дни месяца**
```json
{
  "title": "Отчетность в Минздрав",
  "description": "Заполнение форм по четным числам",
  "recurrence": {
    "type": "even_odd",
    "is_even": true
  }
}
```

**4. Конкретные даты**
```json
{
  "title": "Квалификационный экзамен",
  "description": "Тестирование персонала",
  "recurrence": {
    "type": "dates",
    "dates": ["2024-06-01T00:00:00Z", "2024-06-15T00:00:00Z"]
  }
}
```

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.
